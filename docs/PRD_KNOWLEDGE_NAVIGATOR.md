## 1. 概要

社内規程・福利厚生・手順書・FAQ・組織情報を横断し、自然言語の質問から
**関連制度 / 関連文書 / 該当箇所 / 問い合わせ先 / 担当部署** を提示するナビゲーションシステム。

### 1.1 回答の基本フォーマット（全フェーズ共通）

```
質問: 結婚したら何か制度ある？

▼ 対象制度
  - 結婚祝金（慶弔見舞金規程 第5条）      … 30,000円 / 申請期限: 入籍後6か月以内
  - 結婚休暇（就業規則 第32条 特別休暇）  … 連続5日 / 入籍後1年以内
▼ 関連文書
  - 慶弔見舞金規程（v2.1 / 2026-04-01施行）
  - 就業規則（v5.0 / 2026-04-01施行）
  - 氏名・住所変更届 手順書
▼ 問い合わせ先
  - 人事部 労務グループ（内線 1234 / hr-roumu@example.com）
  - 総務部 庶務グループ（慶弔見舞金の支給）
▼ よくある質問
  - Q. 入籍前に申請できますか？
```

**この4ブロック構造（制度・文書・窓口・FAQ）はPhase1から固定し、Phase5以降のAI回答はこの上に「回答文」を追加するだけ**とする。

## 2. 対象ユーザーとロール

| 利用者 | システムロール | 備考 |
|---|---|---|
| 一般社員 / 新入社員 | `EMPLOYEE` | 新入社員は属性（入社日）で「入社時ガイド」を出し分け |
| 管理職 | `MANAGER` | 管理職向け文書（部下の労務手続き等）を閲覧可 |
| 人事担当 / 総務担当 | `CONTENT_EDITOR` | **自部署が所管するコンテンツのみ** 編集可 |
| 情報システム担当 | `SYSTEM_ADMIN` | ユーザー・権限・マスタ・監査ログ管理。コンテンツ本文の編集は不可（職務分離） |

## 4. MVP定義

### 4.1 MVPのゴール

> 「ダミー規程10本・制度30件・FAQ50件・窓口15件」が登録された状態で、
> 評価用質問50問のうち **35問以上（Hit@5 ≥ 70%）で正しい制度または文書を上位5件に提示し、全件で問い合わせ先を表示** できる。

### 4.2 MVPに含める

- F-101〜F-114（Must全て）
- Markdown本文の文書登録（PDFは含めない）
- 辞書は「ナビゲーションキーワード（語 → 制度/きっかけ）」のみ（汎用類義語辞書はPhase3）
- 日本語部分一致は **pg_bigm**（PDF取込が無くても本文検索に必要なため前倒し）
- デモ用ダミーデータ一式（シードスクリプト）と評価用質問セット
- docker compose で一発起動

### 4.3 MVPから外す（意図的に削る）

| 削る機能 | 理由 |
|---|---|
| PDF取込・OCR | 解析品質の作り込みが重く、MVP価値（ナビゲーション）と独立 |
| SSO / OIDC | デモユーザーで十分。ロール設計だけ先に確定させる |
| 承認ワークフロー（下書き→承認→公開） | 状態遷移だけ持ち、承認者機能は後回し |
| 推薦・サジェスト | ログが溜まってから |
| ベクトル検索・LLM | AIなしで成立することを先に証明する |
| 多言語、通知、Teams連携 | スコープ外 |

### 代表ユースケース詳細: UC-01

- **事前条件**: ログイン済み
- **基本フロー**
  1. 社員が「結婚したら何か制度ある？」と入力
  2. システムがクエリを正規化（NFKC、口語の除去: 「したら」「ある？」）
  3. ナビゲーションキーワード辞書で「結婚」→ きっかけ「結婚」→ 制度群を取得
  4. 文書セクション・FAQ・制度を全文検索
  5. **利用者の権限で見えるものだけ** をスコアリングし、制度/文書/FAQ/窓口の4ブロックで返す
  6. 窓口は「制度の担当窓口」→「文書の所管部署の代表窓口」の順で導出
  7. 検索ログを記録
- **代替フロー**: ゼロヒット時 → 「総合窓口（人事部 代表）」と人気のきっかけ一覧を表示、ゼロヒット語として記録
- **事後条件**: 検索ログ1件、クリック時にクリックログ

## 7. 権限設計

### 7.1 ロール × 操作マトリクス

| 操作 | EMPLOYEE | MANAGER | CONTENT_EDITOR | SYSTEM_ADMIN |
|---|---|---|---|---|
| 検索・閲覧（公開範囲内） | ○ | ○ | ○ | ○ |
| 管理職限定コンテンツ閲覧 | × | ○ | ○(所管分) | × ※1 |
| 文書/制度/FAQ 作成・編集 | × | × | ○ **所管部署のみ** | × ※2 |
| 文書 公開・アーカイブ | × | × | ○ 所管部署のみ | × |
| キーワード/類義語辞書 | × | × | ○ | ○ |
| 部署・窓口マスタ | × | × | 窓口の連絡先のみ(自部署) | ○ |
| ユーザー・ロール管理 | × | × | × | ○ |
| 検索分析ダッシュボード | × | × | ○(所管カテゴリ) | ○ |
| 監査ログ閲覧 | × | × | × | ○ |
| 下書き・非公開の閲覧 | × | × | ○ 所管部署のみ | × |

※1 情シスは技術管理者であり、内容を見る権限とは分離する（最小権限）。障害調査時は監査ログ付きの一時権限で対応。
※2 職務分離。情シスがコンテンツを改ざんできない構造にする。

### 7.2 コンテンツの公開範囲（Visibility）

| 区分 | 値 | 見える人 |
|---|---|---|
| 社内公開 | `INTERNAL` | 全ログインユーザー |
| 管理職限定 | `MANAGERS` | MANAGER以上 |
| 部署限定 | `RESTRICTED` | `access_rules` に指定された部署/ロールのみ |
| 機密 | `CONFIDENTIAL` | 明示的に許可されたユーザーのみ。**検索インデックス・Embedding対象外**（MVPでは登録不可にする） |

- 判定ロジックは **単一の `AccessPolicy` コンポーネント** に集約し、検索・閲覧・API・RAG全経路で共有する。
- 検索SQLには必ず可視範囲条件を WHERE 句で付与（ポストフィルタ禁止 → 件数やスニペットから存在が漏れるため）。
