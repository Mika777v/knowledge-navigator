# ADR-0012: ベクトルは、変更のたびのジョブではなく、定期的な差分合わせで作る

- ステータス: Accepted
- 日付: 2026-10-26
- 関連 Issue / PR: E13-T3（TASKS.md）、#17（Epic E13）、#152（embeddings 表）
- 関連ドキュメント: [ADR-0006](./0006-ai-service-stateless.md)（決定 3 を変更）、[ADR-0007](./0007-pgvector.md)、[ADR-0008](./0008-llm-provider-abstraction.md)、[ARCHITECTURE.md §5.2](../ARCHITECTURE.md)

## 背景（Context）

- ADR-0006 の決定 3 では、版の公開・制度や FAQ の更新のたびに PostgreSQL のキューへジョブを積み、backend のワーカーがベクトルを作ることにしていた。
- ベクトルを作り直す・消す必要があるのは、更新のときだけではない。
  - 版の公開・取り下げ、文書の廃止、FAQ・制度の公開・非公開・削除
  - 公開範囲の変更（`CONFIDENTIAL` になったもの・外部に送ってよい範囲から外れたものは消す。ADR-0008）
  - ai-service のモデルの切り替え（新しいモデルで全部作る）
- 変更のたびにジョブを積む形だと、content モジュールのすべての更新処理にジョブを積む処理を足す必要があり、積み忘れ（とくに削除・公開範囲の変更）がそのまま「残ってはいけないベクトルが残る」ことになる。
- 対象の量は小さい（ダミーデータで条が数百、将来も数万）。全件の `content_hash` を比べても数十ミリ秒〜数秒で済む。

## 決定（Decision）

1. **backend のワーカーが、一定の間隔（既定 5 分。`knavi.embedding.sync-interval`）で「今あるべきベクトル」と `embeddings` 表を見比べる。**
   - あるべきもの: 公開中の最新の版の条、公開中の FAQ・制度のうち、`CONFIDENTIAL` でなく、ADR-0008 の「送ってよい公開範囲」に入るもの。それぞれの文章（見出しパスを先頭に付け、長い条は区切る）と、その SHA-256
   - 足りないもの・`content_hash` が変わったものは、ai-service でベクトルにして保存する（1回に送る数は ai-service の上限以下に分ける）
   - あるべきでない行（元がない・公開をやめた・範囲から外れた・今のモデルでない）は消す
2. **ジョブの表は作らない。** 何をすべきかは毎回 DB の今の状態から決めるので、積み忘れ・二重実行の心配がない（同時に2台動いても、`pg_try_advisory_lock` で1台だけが合わせる）。
3. **モデルは ai-service の `/v1/info` から取る。** モデルが替わったら、新しいモデルの行を作り終えるまでベクトル検索は使わない（ADR-0007 の決定 6 のとおり、検索は今のモデルの行だけを見る）。
4. ai-service に繋がらないとき・失敗したときは、その回を諦めて次の回にやり直す。検索はキーワード検索だけで動き続ける（ADR-0006）。
5. 設定 `knavi.search.vector.enabled` が `false` のときは、合わせる処理も動かさない。

ADR-0006 のそれ以外の決定（ai-service は DB に接続しない、など）は変えない。

## 検討した選択肢（Options）

| 選択肢 | 長所 | 短所 |
|---|---|---|
| 定期的な差分合わせ（採用） | 削除・公開範囲の変更・モデルの切り替えも同じ仕組みで追いつく。積み忘れがない。ジョブの表が要らない | 反映が最大で間隔ぶん（既定 5 分）遅れる。毎回、全件のハッシュを比べる |
| 変更のたびにジョブを積む（ADR-0006 の当初の決定） | 反映が速い。変わったものだけを扱う | content モジュールのすべての更新処理に積む処理が要る。積み忘れが漏えい（消すべきベクトルが残る）につながる。ジョブの表が要る |
| 両方（ジョブで速く、定期的な合わせで取りこぼしを拾う） | 速く、漏れもない | 仕組みが2つになり、今の規模には過剰 |

## 結果（Consequences）

### 良い影響

- 「残ってはいけないベクトル」が、最大でも間隔ぶんの時間で消える。content モジュールの更新処理を触らずに済む（モジュールの境界も保てる）。
- モデルの切り替え・再計算も、同じ処理がそのまま行う。

### 悪い影響・受け入れるリスク

- 公開した規程が意味検索に出るまで、最大で 5 分ほどかかる（キーワード検索にはすぐ出る）。
- 対象が大きく増えると、毎回の見比べが重くなる。

## 検証方法（Compliance）

- 公開・更新・削除・公開範囲の変更（`CONFIDENTIAL` へ）・モデルの切り替えのそれぞれで、1回合わせた後の `embeddings` が「あるべきもの」と一致することをテストで確かめる（ai-service は差し替える）。
- ai-service が失敗したとき、表を壊さずに次の回でやり直すことをテストで確かめる。

## 見直す条件（Revisit when）

- 対象が数十万件を超え、毎回の見比べが重くなったとき（変更のたびのジョブを足す）。
- 公開してすぐに意味検索に出す必要が出たとき。
