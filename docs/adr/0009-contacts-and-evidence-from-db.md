# ADR-0009: AI 回答の窓口・根拠表示は LLM 生成ではなく DB 値から描画する

- ステータス: Proposed
- 日付: 2026-10-28
- 関連 Issue / PR: #18（Epic E14）、E14-T1・T3・T4・T5（TASKS.md）
- 関連ドキュメント: [PRD §1.1・§3 Phase5〜6](../PRD_KNOWLEDGE_NAVIGATOR.md)、[ARCHITECTURE.md §5.4・§5.5](../ARCHITECTURE.md)、[DOMAIN_MODEL.md §3.2](../DOMAIN_MODEL.md)、[ADR-0003](./0003-program-as-first-class-entity.md)、[ADR-0004](./0004-permission-prefilter.md)、[ADR-0008](./0008-llm-provider-abstraction.md)、[ADR-0013](./0013-rag-generation-model-and-delivery.md)

## 背景（Context）

- v0.5.0 では、検索結果をもとに LLM が回答文を書く（RAG）。PRD は「回答には必ず根拠文書・参照箇所・問い合わせ先を出す」「問い合わせ先は LLM 生成ではなく DB の制度→窓口の紐づけから出す」を必須の要件にしている。
- LLM は、もっともらしい間違い（存在しない条番号・古い内線番号・別の部署のメール）を書くことがある。窓口や根拠を間違えると、利用者は間違った相手に申請・相談してしまう。
- 窓口の決め方は、v0.1.0 からナビゲーション検索（`/navigate`）に決まりがある（DOMAIN_MODEL.md §3.2。制度の窓口 → 辞書の窓口 → FAQ の窓口 → 総合窓口）。
- 文書には公開範囲があり、見えないものは件数からも漏らさない（ADR-0004）。外部の LLM に送ってよい公開範囲も決めてある（ADR-0008 決定 5）。

## 決定（Decision）

1. **窓口は、ナビゲーション検索と同じ決まりで backend が DB から決める。** 回答の画面に出す窓口は、`/navigate` と同じ導出（制度の `program_contacts` → 辞書 → FAQ → 総合窓口）で決めた DB の値だけにする。回答できないとき（ADR-0013）も、同じ窓口を出す。
2. **LLM には窓口の連絡先を渡さず、書かせない。** 文脈に入れるのは条の本文だけにし、メール・電話・内線は入れない。プロンプトで「問い合わせ先は書かない（画面に別に出る）」と指示する。回答文にメールアドレス・電話番号の形の文字列があれば、引用検証で不合格にする（ADR-0013）。
3. **根拠は、番号だけを LLM に書かせ、表示は DB から作る。** backend が文脈の条に `[1]`〜`[k]` の番号を付けて、番号と条（section）の ID の対応表を持つ。ai-service が返すのは回答文と、使った番号だけ。画面の根拠（文書名・版・条・ページ・抜粋）は、backend が対応表から section を引いて DB の値で描く。LLM が書いた文書名・条番号は表示に使わない。
4. **文脈に入れる条は、権限で絞った検索結果だけにする。** ハイブリッド検索（`AccessPolicy.readPredicate(..., SEARCH)` で絞ったもの）の上位から選ぶ。外部に送るプロバイダのときは、さらに `knavi.ai.external-visibilities` に入る公開範囲だけにする（ADR-0008）。根拠を描くときにも、同じ利用者で読めるかを確かめ直す。
5. **回答の4ブロックは変えない。** 画面は v0.1.0 からの「制度・文書・窓口・FAQ」の4ブロックをそのまま出し、その上に「回答文」と「根拠」を足すだけにする（PRD §1.1）。

## 検討した選択肢（Options）

| 選択肢 | 長所 | 短所 |
|---|---|---|
| 窓口・根拠は DB から描き、LLM は回答文と番号だけ（採用） | 窓口・条番号が必ず正しい。権限の判定が backend の1か所にまとまる。v0.1.0 の4ブロックをそのまま使える | 「この件は総務部へ」のような、文脈に合わせた窓口の言い回しはできない |
| LLM に窓口・根拠も書かせ、DB と照合する | 文章として自然 | 照合の仕組みが重い。照合に漏れがあると間違った窓口が出る |
| LLM に窓口・根拠も書かせる（照合しない） | 作るのが簡単 | 必須の要件（窓口は DB 由来）を満たさない |

## 結果（Consequences）

### 良い影響

- 回答文がどれだけ間違っても、窓口と根拠の文書・条は正しいものが出る。
- 回答できないときも、検索で決まった窓口へ案内できる（PRD F-503）。
- LLM に渡す情報が減り、外部のプロバイダに送る量も減る。

### 悪い影響・受け入れるリスク

- 回答文の中身（要約）が根拠と合っているかは、番号の照合だけでは保証できない。数値の照合（ADR-0013）と RAG の評価（E14-T6）で確かめる。
- 回答文に「人事部へ」と書かせないため、文章がやや素っ気なくなる。

## 検証方法（Compliance）

- backend のテストで、SSE で返す窓口・根拠が DB の値と一致し、ai-service の応答の文字列を使っていないことを確かめる（ai-service の応答に偽の文書名・連絡先を入れても、画面用の値が変わらない）。
- 権限マトリクスのテストに、回答（`/assistant/answers`）の経路を足す。読めない条が文脈にも根拠にも入らないことを確かめる。
- ai-service のテストで、回答文に連絡先の形の文字列があれば不合格になることを確かめる。

## 見直す条件（Revisit when）

- AI アシスタント（v0.6.0）で、窓口を選ぶ確認の質問など、窓口の言い回しを会話に合わせたくなったとき。
- 窓口の決め方そのもの（DOMAIN_MODEL.md §3.2）を変えるとき。
