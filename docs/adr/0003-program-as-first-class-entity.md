# ADR-0003: 制度（Program）を文書から独立したエンティティにする

- ステータス: Accepted
- 日付: 2026-10-20
- 関連 Issue / PR: #22, #33（制度・きっかけ・FAQ の API）
- 関連ドキュメント: [DOMAIN_MODEL.md §1, §3](../DOMAIN_MODEL.md), [PRD_KNOWLEDGE_NAVIGATOR.md §1.1](../PRD_KNOWLEDGE_NAVIGATOR.md), [DESIGN_REVIEW.md §7](../DESIGN_REVIEW.md)

## 背景（Context）

- 利用者の課題は「どの文書を見ればよいかわからない」「制度名がわからない」「誰に聞けばよいかわからない」。
- 利用者が知りたいのは文書そのものではなく、**自分が使える制度**（結婚祝金、結婚休暇、通勤手当…）と、その**申請方法・期限・問い合わせ先**である。
- 1つの制度の情報は複数の文書にまたがる（例: 結婚休暇は就業規則、申請手順は手順書、窓口は組織情報）。逆に1つの文書には多数の制度が含まれる。
- 文書検索だけで作ると、検索結果は「文書の一覧」になり、利用者は文書を開いて自分で該当箇所を探すことになる。これは現状（共有フォルダの PDF）と変わらない。
- 将来の RAG（Phase5）では、窓口や適用条件を LLM に推測させると誤りが起きやすい（DESIGN_REVIEW.md §6）。

## 決定（Decision）

1. **制度（Program）を独立した集約ルート** とし、次の属性を構造化して持つ: 名称・概要・対象者・金額/日数・申請方法・期限・必要書類・所管部署・公開範囲。
2. 制度は次と多対多で紐づける。
   - 根拠（`program_basis`）: 文書と条文セクション
   - 窓口（`program_contacts`）: 役割（申請先 / 問い合わせ先 / 支給担当）つき
   - きっかけ（`life_event_programs`）: 結婚・出産・引越し などの状況
   - FAQ（`faq_links`）
3. ドメインの不変条件として以下を強制する。
   - 公開する制度には窓口が1件以上必要。
   - 制度の公開範囲は、根拠文書の公開範囲より広くしてはいけない。
4. 検索結果は「制度 / 文書・該当箇所 / FAQ / 問い合わせ先」の4ブロックで返し、制度が見つかれば根拠条文と窓口を必ず添える。
5. AI 回答（Phase5〜6）でも、窓口・根拠・適用条件はこの構造化データから表示し、LLM には生成させない（将来の ADR-0009）。

## 検討した選択肢（Options）

| 選択肢 | 長所 | 短所 |
|---|---|---|
| **A. 制度を独立エンティティにする（採用）** | 「状況 → 制度 → 根拠 → 窓口」を確実に辿れる、AI なしで価値が出る、RAG の誤りを構造化データで防げる | 制度データの整備・保守の手間がかかる |
| B. 文書とタグだけで表現する | データ整備が少ない | 申請方法・期限・窓口が文書本文に埋もれ、結果は文書一覧止まり。窓口を必ず返す保証ができない |
| C. 制度は LLM で文書から都度抽出する | 整備の手間がない | 結果が不安定で検証できない、誤った金額や期限を提示するリスク。Phase1 では AI を使わない方針にも反する |

## 結果（Consequences）

### 良い影響

- 制度名を知らない利用者も、きっかけ（結婚など）やキーワード辞書から制度に到達できる。
- 窓口が制度に紐づくため、ゼロヒット時を含めて必ず問い合わせ先を返せる。
- RAG 導入後も、根拠と窓口の正しさをデータ側で保証できる。

### 悪い影響・受け入れるリスク

- 制度データの整備が運用負荷になる（DESIGN_REVIEW.md R1）。初期は上位30制度に絞り、将来は LLM による下書き生成 + 人のレビューで補う。
- 規程の改定でセクションが再分割されると、根拠リンクが古い版を指す。`program_basis` に `document_id` も保持し、改定時に再リンクを支援する（技術的負債 D6）。
- 文書と制度で情報が二重になり、食い違う可能性がある。制度には根拠条文へのリンクを必須にし、正本は規程側と明示する。

## 検証方法（Compliance）

- 不変条件（窓口1件以上・公開範囲の大小関係）をドメイン層の単体テストで検証する。
- 評価用質問セットで「制度の正答率」「窓口の正答率」を計測する（#39）。

## 見直す条件（Revisit when）

- 制度の件数が増えて人手での保守が回らなくなったとき（LLM による抽出支援の導入を検討）。
- 人事システム側に制度マスタが存在し、同期で取り込めるようになったとき。
