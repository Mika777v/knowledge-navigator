# ADR-0004: 権限フィルタは検索前（プレフィルタ）に適用する

- ステータス: Accepted
- 日付: 2026-10-20
- 関連 Issue / PR: #22, #34（AccessPolicy）, #38（権限マトリクステスト）
- 関連ドキュメント: [PRD_KNOWLEDGE_NAVIGATOR.md §7](../PRD_KNOWLEDGE_NAVIGATOR.md), [ARCHITECTURE.md §6](../ARCHITECTURE.md), [DESIGN_REVIEW.md §3-4](../DESIGN_REVIEW.md)

## 背景（Context）

- 社内文書には公開範囲がある（INTERNAL / MANAGERS / RESTRICTED / CONFIDENTIAL）。管理職限定の手順書や、特定部署限定の規程が含まれる。
- 検索結果は文書本体だけでなく、件数・スニペット・制度カード・FAQ・サジェスト・関連推薦・（Phase5 以降の）RAG の回答文脈など、多くの経路で情報を表示する。
- よくある実装は「関連度の高い上位 N 件を取ってから、権限のないものを除外する」ポストフィルタだが、次の問題がある。
  - 件数やページングがずれ、「何か見えないものがある」ことが推測できる。
  - スニペットやサジェストなど、除外処理を通らない経路から内容が漏れる。
  - 上位 N 件がすべて権限外だと、見えるはずの結果が0件になる。
- 権限の判定ロジックが経路ごとに実装されると、どこか1か所の漏れが情報漏えいになる。

## 決定（Decision）

1. **権限フィルタは候補を取得する SQL の WHERE 句で適用する（プレフィルタ）。** 関連度の計算は、権限で絞り込んだ後の集合に対してだけ行う。
2. 判定ロジックは **`AccessPolicy` に一本化** する。`AccessPolicy` はログインユーザーから `AccessScope`（ロール・所属部署・ユーザー ID）を作り、検索 SQL に付与する述語を生成する。
3. 次のすべての経路で同じ `AccessScope` を使う。
   - 検索（制度・セクション・FAQ）、件数、スニペット、ハイライト
   - サジェスト、人気クエリ、関連推薦、類似条文（Phase4）
   - RAG の検索と文脈構築（Phase5）。ai-service には backend が確定させたスコープを渡し、ai-service 自身は認可を持たない。
4. 関連付け経由の表示（制度カード内の根拠文書名など）も、表示時に根拠ごとに再判定する。
5. CONFIDENTIAL の文書は、検索インデックス・Embedding・LLM への送信の対象外とする。
6. ポストフィルタ（取得後の除外）を新たに実装することは禁止する。

### 判定ルール（要約）

| 公開範囲 | 見える人 |
|---|---|
| INTERNAL | ログインユーザー全員 |
| MANAGERS | MANAGER 以上のロール |
| RESTRICTED | `access_rules` で許可された部署・ロール・ユーザー |
| CONFIDENTIAL | `access_rules` で明示的に許可されたユーザーのみ（検索対象外） |

下書き（DRAFT）は所管部署の CONTENT_EDITOR だけが見られる。SYSTEM_ADMIN はコンテンツを閲覧・編集できない（職務分離）。

## 検討した選択肢（Options）

| 選択肢 | 長所 | 短所 |
|---|---|---|
| **A. SQL によるプレフィルタ + AccessPolicy 集約（採用）** | 漏えい経路が構造的に少ない、件数・ページングが正しい、権限変更が即時反映 | 検索 SQL が複雑になる、述語の性能に注意が必要 |
| B. 取得後のポストフィルタ | 実装が簡単 | 件数・スニペット・サジェストから漏れる、結果が0件になる問題 |
| C. PostgreSQL の行レベルセキュリティ（RLS） | DB 側で強制でき、アプリのバグに強い | セッション変数の受け渡しや接続プールとの相性、デバッグの難しさ。MVP では A を採用し、将来の多層防御として検討 |
| D. 検索エンジン側に権限を複製（OpenSearch のドキュメントレベルセキュリティ等） | 大規模でも高速 | 権限の同期遅延がそのまま漏えいリスクになる（ADR-0002 で不採用） |

## 結果（Consequences）

### 良い影響

- 「見えてはいけないものは候補にすら入らない」ため、件数やスニペット経由の漏えいを構造的に防げる。
- 権限ロジックが1か所なので、テストとレビューの対象が明確になる。
- RAG でも、LLM に渡る文脈は権限内のものだけになる。

### 悪い影響・受け入れるリスク

- 新しい検索経路を追加する開発者が `AccessPolicy` を通し忘れるリスク → アーキテクチャテストで検出する。
- `access_rules` の EXISTS 句が検索性能に影響する可能性 → 大半の行は公開範囲の enum だけで判定でき、例外のみ `access_rules` を参照する設計で抑える。
- LLM 応答をキャッシュする場合、ユーザー間で共有すると権限差で漏えいする → キャッシュキーにスコープを含める（Phase5）。

## 検証方法（Compliance）

- **権限マトリクステスト（#38）**: ロール × 公開範囲 × 操作 × 経路（検索 / 閲覧 / API）の組み合わせをパラメタライズドテストで網羅し、CI で必須にする。
- 件数・スニペットから権限外の存在が推測できないことをテストする。
- アーキテクチャテストで、`content` などのリポジトリへの検索クエリが `AccessPolicy` を経由していることを検証する。
- PR テンプレートのチェック項目「権限に影響する変更の場合、権限マトリクステストを更新した」を必ず確認する。

## 見直す条件（Revisit when）

- 検索基盤を PostgreSQL 以外（OpenSearch 等）に移すとき（権限の同期方式を別 ADR で決める）。
- 多層防御として RLS を導入するとき。
- 外部 IdP のグループで権限を管理する方式に変わったとき。
