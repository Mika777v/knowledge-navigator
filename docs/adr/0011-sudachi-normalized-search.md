# ADR-0011: 表記ゆれ・活用のちがいは、backend の Sudachi で正規化形にそろえ、pg_bigm の検索列を足して吸収する

- ステータス: Proposed
- 日付: 2026-10-26
- 関連 Issue / PR: E12-T1（TASKS.md）、#16（Epic E12）、#123（類義語辞書）
- 関連ドキュメント: [ARCHITECTURE.md §4.1〜4.3](../ARCHITECTURE.md)、[PRD F-302](../PRD_KNOWLEDGE_NAVIGATOR.md)、[ADR-0002](./0002-japanese-search-pg-bigm.md)、[ADR-0004](./0004-permission-prefilter.md)

## 背景（Context）

- 今の検索は、質問から「漢字・カタカナ・英数字が2文字以上続く部分」を語として取り出し、pg_bigm の `LIKE '%語%'` で探している（ADR-0002）。
- この方法では、次のような質問を取りこぼす（評価用の100問で外れている質問。#122）。
  - **活用のちがい**: 「お祝い金はいつ**振り込まれる**？」の語は「祝」「金」「振」の1文字ずつになり、語として取り出せない。FAQ は「いつ**振り込まれますか**」
  - **ひらがなの動詞**: 「親の通院に**付き添う**」「病院へ行くため**抜けたい**」は語として取り出せない
  - **表記ゆれ**: 「引越し／引っ越し／引越」「子供／子ども／こども」「慶弔見舞金／慶弔見舞い金」は文字が違うため、片方でしか一致しない
- 類義語辞書（#123）は「意味が同じ別の言葉」（育休＝育児休業）を人が登録するもので、活用・表記ゆれを1つずつ登録するのは現実的でない。
- PRD F-302 は「全角半角・ひらがなカタカナ・形態素解析の正規化形」で表記ゆれを吸収することを求めている。ARCHITECTURE.md §4.1 は Phase3 で「Sudachi の正規化形を併用する」と書いている。
- 権限は、検索と同じ SQL の中で絞り込む（ADR-0004）。検索の方式を変えても、この形は崩さない。

## 決定（Decision）

1. **形態素解析には Sudachi（Java 版）を backend の中で使う。** ライブラリは `com.worksap.nlp:sudachi:0.8.2`（Apache License 2.0。2026-09-18 公開）、辞書は **SudachiDict core 20260723.1**（Apache License 2.0。2026-09-24 公開）。分割は C モード（最も長い単位。「在宅勤務」「育休明け」を1語にする）、各語は **正規化形**（振り込まれ → 振り込む、引越 → 引っ越し、子ども → 子供、シュミレーション → シミュレーション）にする。
2. **検索用の列を足し、pg_bigm で探す。** 制度・条・FAQ に、正規化形を空白で区切って並べた `search_norm` 列（text）を足し、`search_text` と同じく pg_bigm の GIN インデックスを張る。今の `search_text` と、その照合（名前・見出しへの一致の重みなど）は残す。
3. **質問も同じ方法で正規化する。** 質問を Sudachi で分け、内容語（名詞・動詞・形容詞など。助詞・助動詞・記号は除く）の正規化形を語にする。複数の語が続く名詞（満員 電車）は、正規化形を空白でつないだ1つの語としても探す。`search_norm` での一致は、`search_text` での一致と同じ重みで足し、同じ語が両方に一致しても二重には数えない。
4. **辞書の照合（ナビゲーションキーワード）と類義語にも正規化形を使う。** キーワード・類義語の語も正規化形にしてから照合する（保存時に作る）。今の語幹での照合（ARCHITECTURE §4.3）は、正規化形で置き換えられることを評価で確かめてから外す。
5. **辞書ファイルはリポジトリに入れず、取り寄せて検証する。** 辞書は約 200MB（圧縮して約 77MB）あるため、git には入れない。
   - 取り寄せ先は PyPI の配布物（`sudachidict_core-20260723.1-py3-none-any.whl`）にする。SHA-256 を固定して確かめ、合わなければ失敗にする
   - backend のイメージのビルド時に取り込む。手元・CI のテストでは Gradle のタスクで取り寄せ、キャッシュする
6. **辞書がないときは、今の方法で動かす（劣化運転）。** 辞書の場所が設定されていない・読めないときは、起動時に警告を出し、今の語の取り出し方と `search_text` だけで検索する。検索そのものは止めない。
7. **辞書の版を変えたら、検索列を作り直す。** 検索列を作ったときの辞書の版を `app_settings`（`search.norm_dictionary`）に記録し、backend の起動時に今の辞書の版と違えば、全件を作り直す（制度・条・FAQ は数千件までの想定で、数秒で終わる）。辞書なしで起動したときは記録を消し、次に辞書ありで起動したときに作り直す。（実装の PR で、管理者が実行するバッチから起動時の自動の作り直しに変えた）

## 検討した選択肢（Options）

### 形態素解析の方法

| 選択肢 | 長所 | 短所 |
|---|---|---|
| **A: Sudachi（Java 版）を backend の中で使う（採用）** | 正規化形（表記ゆれ・活用をそろえた形）を辞書が持っている。検索向けの C モードで複合語を1語にできる。backend だけで完結し、サービスが増えない。辞書の読み込みは約 0.15 秒（試した値） | 辞書が大きい（約 200MB。イメージとメモリが増える）。辞書の版を上げると検索列の作り直しが要る |
| B: Kuromoji（Lucene の日本語解析） | 軽い。実績が多い | 正規化形を持たない（原形はあるが、「引越／引っ越し」「子ども／子供」はそろわない） |
| C: PGroonga（PostgreSQL の拡張） | DB の中で日本語の全文検索ができる | ADR-0002 で見送った理由（マネージド DB での提供状況・独自イメージのビルド）がそのまま残る。正規化形はそろわない |
| D: Python（SudachiPy）の別サービスにする | Phase4 の ai-service と同じ言語 | v0.3.0 の時点でサービスと通信が増える。保存のたびに別サービスを呼ぶ必要がある |

### 正規化形の持ち方

| 選択肢 | 長所 | 短所 |
|---|---|---|
| **A: 正規化形の文字列の列を足し、pg_bigm で探す（採用）** | 今の SQL・重み付け・権限の絞り込み（ADR-0004）をそのまま使える。複数の語の並び（満員 電車）も `LIKE` で探せる | 2-gram のため、語の境目をまたいだ一致も拾う（正規化形の空白で、ある程度は防げる） |
| B: `tsvector`（simple 構成）の列を足し、`@@` と `ts_rank` で探す | 語の単位で一致を判定できる。順位付けの関数がある | 今の pg_bigm の点数と別の物差しになり、統合と重みの調整が難しくなる。語の並びの一致には `<->` などの別の書き方が要る |
| C: `search_text` を正規化形に置き換える | 列が増えない | 名前・見出しへの一致（原文での一致）の判定が変わり、今の評価の結果を保てるか分からない。元に戻しにくい |

### 辞書の配り方

| 選択肢 | 長所 | 短所 |
|---|---|---|
| **A: ビルド時に取り寄せ、SHA-256 で確かめる（採用）** | リポジトリが大きくならない。版とファイルの中身を固定できる | ビルドに外部への接続が要る（CI・Docker のビルドでは使える） |
| B: git（LFS）に入れる | 外部への接続が要らない | リポジトリが大きくなる。LFS の容量の制限がある |
| C: small 辞書（約 42MB）を使う | 小さい | 語の数が少なく、複合語・表記ゆれの取りこぼしが増える。評価で比べて core で足りない場合の候補にする |

## 結果（Consequences）

### 良い影響

- 活用・表記ゆれ・ひらがなの動詞を含む質問が、FAQ・条文に届くようになる（評価用の100問で、取りこぼしの理由の多くがこれ）。
- 類義語辞書には「意味が同じ別の言葉」だけを登録すればよくなる。
- 検索の SQL・権限の絞り込みの形は変わらない。

### 悪い影響・受け入れるリスク

- backend のイメージが約 200MB、使うメモリが辞書の分だけ増える（辞書はファイルを読み込んで使う）。Codespaces（4コア）での `make up` の時間が少し延びる。
- 制度・条・FAQ の保存のたびに形態素解析をする（1件あたり数ミリ秒の見込み。取り込みのジョブでは条の数だけかかる）。
- 辞書の版を上げるたびに、検索列の作り直しと評価のやり直しが要る。
- Sudachi の正規化形が意図とずれる語（固有の略語など）がある。そのときは類義語辞書・キーワードで補う。

## 検証方法（Compliance）

- 評価用の100問（`make eval`）で、導入の前後を比べる。v0.3.0 の目標（Hit@5 ≥ 85%、ゼロヒット率 < 10%）を下回らず、Hit@1・MRR が下がらないこと。1問ずつの順位も比べ、下がった質問は PR に書く。
- 辞書がないときに今の方法で動くことを、テストで確かめる（辞書なしの設定で検索の API テストを流す）。
- 権限の絞り込みは、既存の権限マトリクステストがそのまま通ること（`search_norm` も同じ WHERE 句の中で使う）。
- 辞書の SHA-256 が合わないとき、取り寄せのタスクが失敗すること。

## 見直す条件（Revisit when）

- Phase4 で ai-service（Python）を置き、解析を Python に移すとき（SudachiPy で同じ辞書を使えるかを確かめる）。
- 辞書の大きさがデモ環境のメモリ・イメージの制限に合わなくなったとき（small 辞書、または別の方式を比べる）。
- 文書の数が増え、pg_bigm での検索が遅くなったとき（ARCHITECTURE §4.5 の OpenSearch への移行の判断基準）。
- Sudachi（Java 版）の保守が止まったとき（今は 2026 年 5 月・9 月に版が出ている）。
