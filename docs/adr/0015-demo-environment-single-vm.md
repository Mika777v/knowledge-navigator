# ADR-0015: デモ環境は、1台の小さな VM で compose を動かし、公開済みのイメージ・AI はオフ・毎日データを初期化する形で公開する

- ステータス: Proposed
- 日付: 2026-10-30
- 関連 Issue / PR: #20（E16-T3 デモ環境デプロイ）
- 関連ドキュメント: [ARCHITECTURE.md §7](../ARCHITECTURE.md)、[ADR-0002](./0002-japanese-search-pg-bigm.md)、[ADR-0005](./0005-nextjs-as-bff.md)、[ADR-0013](./0013-rag-generation-model-and-delivery.md)

## 背景（Context）

ポートフォリオとして、リポジトリを読む人が**URL を開くだけで画面を触れる**デモ環境がほしい（E16-T3）。ARCHITECTURE §7 には「単一VM or コンテナPaaS + マネージドPostgreSQL」とだけ書いてあり、どれにするかは決めていなかった。

前提と制約:

- **DB は pg_bigm と pgvector を入れた自前の PostgreSQL 17 のイメージ**（ADR-0002・0007）。マネージドの PostgreSQL で pg_bigm を入れられるものは限られ（Amazon RDS は対応。ほかは提供元ごとに確かめる必要がある）、入れられないと検索が動かない。DBMS は PostgreSQL のまま変えない
- 画面と API は**同じオリジン**にする（ADR-0005）。Next.js が `/api/*` を backend に中継する今の形をそのまま使いたい
- 動かすものは postgres・SeaweedFS（PDF の原本）・backend（JVM）・frontend。合わせてメモリ 2〜3GB ほど。AI（ai-service + Ollama の qwen3.5:4b）を足すと数 GB 増え、CPU だけでは回答に時間がかかる
- イメージはリリースのタグで ghcr.io に公開済み（release-images.yml。amd64）
- **誰でもデモユーザーでログインできる**。デモユーザーには規程を編集できるコンテンツ担当者・ユーザーを管理できるシステム管理者もいて、パスワードの変更もできる。見た人がデータを書き換えたり、パスワードを変えて他の人が入れなくしたりできる
- オーナーは運用に詳しくない前提。費用は月に数百〜千円台まで、手間は「タグを作ったら上げ直す」程度に抑えたい

## 決定（Decision）

1. **1台の小さな VM（amd64、メモリ 4GB 以上）で Docker Compose を動かす。** VM の提供元は特定のものに縛らず、オーナーが契約できるものを選ぶ（要件だけを決める）
2. 本番用の compose ファイル（`compose.demo.yaml`）を足し、**ghcr.io に公開した版のイメージ**を版を指定して取得する。VM の上でビルドしない
3. 前に **Caddy** を置き、HTTPS（Let's Encrypt の証明書を自動で取得・更新）で frontend だけを外に出す。backend・postgres・SeaweedFS は外に出さない（同じオリジン、ADR-0005 のまま）
4. **AI はオフ**にする（`KNAVI_SEARCH_VECTOR_ENABLED=false`・`KNAVI_ASSISTANT_ENABLED=false`。ai-service・Ollama は起動しない）。キーワード検索・閲覧・きっかけの案内（判定は DB の条件。ADR-0014）・管理画面は動く。根拠付きの回答は README の画像・動画で見せる
5. **毎日1回、DB と原本を消してダミーデータを入れ直す**（VM の cron から `docker compose` で初期化 → `seed`）。見た人が書き換えても翌日には戻る。画面の上部に「デモ環境です。データは毎日初期化されます」と出す
6. デモで困る操作（パスワードの変更・ユーザーの無効化など、他の見る人を締め出せるもの）は、**デモ用の設定でオンのときだけ止める**。認証・権限まわりの変更になるため、別の PR でオーナーに確認してから入れる
7. 秘密の値（DB のパスワード・HMAC の鍵など）は VM の `.env` にだけ置き、リポジトリには `.env.demo.example`（値は空）だけを置く

## 検討した選択肢（Options）

| 選択肢 | 長所 | 短所 |
|---|---|---|
| A. 1台の VM で compose（採用） | 手元・CI と同じ compose の形でそのまま動く。自前の PostgreSQL イメージ（pg_bigm）をそのまま使える。費用が月額で決まり、予想しやすい。提供元を変えても手順はほぼ同じ | OS の更新・ディスクの空き・証明書などを自分で見る必要がある（Caddy と自動更新で減らす）。1台なので止まるときは全部止まる（デモなので受け入れる） |
| B. コンテナ PaaS（Fly.io・Render・Azure Container Apps など）+ マネージド PostgreSQL | サーバの面倒を見なくてよい。デプロイが画面やコマンド1つで済む | pg_bigm を入れられるマネージド PostgreSQL が限られ、無ければ DB もディスク付きのコンテナとして PaaS で動かすことになる（B の長所が薄れる）。サービスが4つあり、サービスごとに課金されて A より高くなりやすい。同じオリジンにするための経路の設定が提供元ごとに違う |
| C. 常時公開しない（Codespaces で各自が起動 + README の画像・動画） | 費用・運用・公開による危険がゼロ。`.devcontainer` はすでにある | 見る人に GitHub のアカウントと数分の待ち時間が要る。「URL を開けば触れる」にならない。→ **A と併せて README に「Codespaces で開く」も置く** |
| D. 無料枠の VM（Oracle Cloud の Always Free など） | 費用がかからない | 無料枠の条件が変わることがある（2026 年に Ampere A1 の枠が半分になったとの報告がある）。Arm なので、イメージを Arm 向けにもビルドする必要がある。条件が合えば A の提供元の一つとして選べる |
| AI もオンにする（A の上で） | 根拠付きの回答・状況の読み取りを触れる | CPU だけの小さな VM では Ollama の回答に時間がかかり、メモリも足りない。外部の LLM（OpenAI など）に切り替えると、誰でも呼べるため費用と乱用の心配がある |

## 結果（Consequences）

### 良い影響

- README のリンクから、ログインして検索・閲覧・案内・管理画面まで触れる
- デモの構成が手元の `make up` と同じ形なので、動かなくなったときに手元で再現しやすい
- AI を使わないので、外部の API の費用・鍵の漏れ・乱用の心配が無い

### 悪い影響・受け入れるリスク

- 月数百〜千円台の費用がかかる（提供元・大きさによる）
- 1台なので、VM が止まるとデモも止まる。監視は外形監視（無料の死活監視サービスなど）だけにする
- デモでは根拠付きの回答・状況の読み取りを触れない（README の画像・動画で補う）
- 見た人が入れた内容は翌日の初期化まで残る。不適切な内容が入る可能性は、毎日の初期化と、締め出しにつながる操作の停止（決定 6）で抑える

## 検証方法（Compliance）

- `compose.demo.yaml` を CI（ci-compose）で起動し、Caddy 経由で `/api/health`・ログイン・検索が通ることを確かめる（証明書は CI では自己署名に切り替える）
- backend・postgres・SeaweedFS のポートを外に出していないことを、compose ファイルのレビューで確かめる
- 毎日の初期化の後に、デモユーザーでログインできることを外形監視で確かめる

## 見直す条件（Revisit when）

- 見る人が増えて 1 台では足りない、または止まると困るようになったとき（B か、A を複数台に）
- 安く使える GPU、または費用の上限を掛けられる LLM の API を使えるようになり、デモで AI をオンにしたくなったとき
- pg_bigm を入れられるマネージド PostgreSQL を使えるようになったとき（B の短所が減る）
