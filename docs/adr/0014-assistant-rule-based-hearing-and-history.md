# ADR-0014: AI アシスタントの確認質問・制度の判定・チェックリストは DB の条件から決まった手順で作り、会話の履歴は本人だけが見られる形で保持期間つきで残す

- ステータス: Proposed
- 日付: 2026-10-30
- 関連 Issue / PR: #19（Epic E15）、E15-T1〜T4（TASKS.md）
- 関連ドキュメント: [PRD §3 Phase6](../PRD_KNOWLEDGE_NAVIGATOR.md)、[ARCHITECTURE.md §5.1](../ARCHITECTURE.md)、[DOMAIN_MODEL.md](../DOMAIN_MODEL.md)、[ADR-0004](./0004-permission-prefilter.md)、[ADR-0009](./0009-contacts-and-evidence-from-db.md)、[ADR-0013](./0013-rag-generation-model-and-delivery.md)

## 背景（Context）

- v0.6.0 では、PRD の Phase6 の4つを試作する。
  - F-601 確認質問（「雇用形態は？」など）で対象の制度を絞る
  - F-602 きっかけ（結婚など）から、使える制度と必要な手続きを漏れなく出す
  - F-603 必要書類・期限・申請先を ToDo（チェックリスト）にする
  - F-604 会話の履歴。自分の履歴だけ見られる。保持期間を決める
- PRD は「Phase6 の回答には必ず根拠文書・参照箇所・問い合わせ先を出す。問い合わせ先は LLM ではなく DB から出す」と決めている（ADR-0009）。ARCHITECTURE §5.1 は「AI が止まっても通常の検索で使える」と決めている。
- 今の DB で、制度の対象者（`programs.eligibility`）は文章で書かれている（例:「勤続6か月以上の正社員・契約社員（パートタイム社員は半額）」）。**機械で「対象か」を判定できる形のデータが無い。** 一方、きっかけ → 制度のつながり（`life_event_programs`。PRIMARY / RELATED）と、必要書類・期限・申請先（`required_documents`・`deadline_note`・`program_contacts` の APPLY）は DB にある。
- 利用者の雇用形態は `users.employment_type` にある。
- 既定の生成モデルは CPU で動く 4B（ADR-0013）。1回の回答に数十秒かかり、数値の写し間違いを照合で捨てている。
- 会話の本文には、家族のこと・病気のことなど、個人の事情が書かれやすい。ARCHITECTURE §6 は「チャット本文は保持期間後に削除」と決めている。

## 決定（Decision）

1. **確認質問・対象かどうかの判定・チェックリストは、LLM を使わず、DB の値から決まった手順で作る**（「案内」と呼ぶ）。
   - 確認質問は DB の表 `assistant_questions`（コード・質問文・選択肢）に置く。最初は次の2つにする（ダミーの規程の対象者の書き方から選んだ）。
     - `EMPLOYMENT_TYPE` 雇用形態（正社員・契約社員・パートタイム社員）。**ログイン中の利用者の `users.employment_type` を初めから選んでおき**、利用者が変えられる
     - `TENURE_6M` 勤続6か月以上か（はい・いいえ）
   - 制度の条件は表 `program_conditions`（制度・質問・当てはまる選択肢の一覧）に置く。データはシード（`programs.yaml` の `conditions`）で入れる。
   - 判定は「その制度のすべての条件で、答えが当てはまる選択肢に入っていれば **対象**、1つでも外れれば **対象外**、答えていない条件があれば **要確認**」。条件の無い制度は対象。**対象外の制度も消さずに理由とともに出す**（文章の `eligibility` もいっしょに出す。判定は目安で、最後は窓口が決めるため）。
   - 質問は、**そのきっかけで、その人が見られる制度**（ADR-0004 の AccessPolicy で絞った後）の条件に出てくるものだけを出す。見られない制度の条件から質問を作らない（質問から制度の存在が漏れないようにする）。
   - チェックリストは、対象・要確認の制度ごとに「必要書類」「期限（`deadline_note` の文章のまま）」「申請先（APPLY の窓口。DB の値）」「根拠の条」を並べる。期限の日付の計算はしない（見直す条件を参照）。
   - 案内の API は状態を持たない（答えを送ると結果が返る）。**答え（雇用形態など）は保存しない。**
2. **自由な質問への回答文は、今の根拠付き回答（ADR-0013）をそのまま使う。** 案内の画面から自由な質問をしたときも同じ SSE を使う。
3. **会話の履歴（自由な質問と、確かめた回答文）は PostgreSQL に残す。**
   - 表は `chat_sessions`（利用者・題名・期限）と `chat_messages`（役割・本文・回答できたか・引用した条の ID）。`chat_sessions.user_id` は users を指す（検索ログのような仮名化はしない。本人が見るため）。
   - **見られるのは本人だけ**にする。API は常にログイン中の利用者の ID で絞る。管理者も他の人の履歴は見られない（管理の API を作らない）。本人は会話を削除できる。
   - 保持期間は既定 **90日**（`knavi.assistant.retention-days`）。最後に話した日から数え、過ぎた会話は毎日の削除処理（検索ログと同じ形）で消す。
   - 履歴を開いたときの引用は、保存した条の ID を**その時点の権限で読み直して**出す。見られなくなった条は出さず、「見られない根拠がある」とだけ出す（中身・題名は出さない）。窓口もその時点の DB の値から出す。
   - 本文はアプリのログに出さない。
4. **backend に `assistant` モジュールを作り、会話と案内を置く**（ARCHITECTURE の予定どおり）。回答文の生成は navigation の `AnswerService` を使う。

## 検討した選択肢（Options）

### 確認質問と判定の作り方

| 選択肢 | 長所 | 短所 |
|---|---|---|
| DB の条件から決まった手順で作る（採用） | 同じ答えなら必ず同じ結果。テストで全部確かめられる。LLM が止まっても動く。速い | 条件の形に当てはまらない対象者（「要介護の家族がいる」など）は判定できず、文章を読んでもらう。条件のデータを用意する手間がある |
| LLM に `eligibility` の文章を読ませて質問と判定を作らせる | データを用意しなくてよい。どんな書き方でも扱える | 4B では判定を間違えやすく、間違いを機械で確かめる方法が無い。毎回数十秒かかる。結果が毎回変わりうる |
| 質問の文だけ LLM に作らせ、判定は DB で行う | 言い回しが自然になる | 決まった選択肢の質問なら、文を作らせる利点が小さい。遅くなる |

### 会話の履歴の置き場所

| 選択肢 | 長所 | 短所 |
|---|---|---|
| PostgreSQL に保持期間つきで残す（採用） | 別の端末からも見られる。保持期間で確実に消せる。権限の読み直しを SQL でできる | 個人の事情を会社のサーバに残す。削除の仕組みが要る |
| ブラウザ（localStorage）だけに残す | サーバに残らない | 端末を変えると見られない。共有の PC で他の人に見られうる。保持期間で消すのを保証できない |
| 残さない | いちばん安全 | PRD の F-604 を満たさない |

### 案内の答え（雇用形態など）の扱い

| 選択肢 | 長所 | 短所 |
|---|---|---|
| 保存しない（採用） | 個人の事情が残らない | 履歴から案内をもう一度開くと、答え直しになる |
| 会話の一部として保存する | 続きから再開できる | 保存する個人の情報が増える |

## 結果（Consequences）

### 良い影響

- 「対象か」「何を出すか」の判定が LLM に左右されず、根拠・窓口・書類はすべて DB の値になる（ADR-0009 と同じ考え）。
- AI（Ollama）が止まっていても、案内（確認質問・制度の一覧・チェックリスト）は使える。止まるのは自由な質問の回答文だけ。
- 判定の表がマトリクスのテストにしやすい。

### 悪い影響・受け入れるリスク

- 「AI アシスタント」のうち、LLM を使うのは自由な質問の回答文だけになる。会話らしさ（自由な文から答えを読み取るなど）は無い。
- 条件を2つの質問に絞るため、子の年齢・介護の有無などで決まる制度は「要確認」か、条件なし（対象）のまま、文章の `eligibility` を読んでもらうことになる。
- DB の表（`assistant_questions`・`program_conditions`・`chat_sessions`・`chat_messages`）が増える。条件の管理画面は作らず、シードだけで入れる。
- 会話の本文が保持期間の間サーバに残る。

## 検証方法（Compliance）

- backend のテストで、案内の判定（対象・対象外・要確認）を、雇用形態 × 勤続の組み合わせで確かめる。見られない制度の条件からは質問が出ないことも確かめる。
- backend のテストで、他の人の会話は一覧にも取得にも出ない（404）こと、保持期間を過ぎた会話が消えること、見られなくなった条が履歴に出ないことを確かめる。
- E2E で、きっかけ → 確認質問 → 制度の一覧 → チェックリストの流れと、履歴の表示・削除を確かめる。
- `validate_seed.py` で、`conditions` の質問・選択肢が決まったものだけであることを確かめる。

## 見直す条件（Revisit when）

- 判定できない対象者の書き方が多く、「要確認」ばかりになるとき（質問を足す。子の年齢など）。
- 期限を日付で出してほしいという要望があるとき（起算日の質問と、期限の月数・日数の列を足す）。
- 条件を管理画面で直したいとき。
- 自由な文から答えを読み取るなど、LLM で会話らしさを足すとき（判定は DB のまま、読み取りだけ LLM にするなど）。
