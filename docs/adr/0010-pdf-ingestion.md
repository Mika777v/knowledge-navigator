# ADR-0010: PDF の取り込みは backend の中で行い、原本は S3 互換ストレージ、解析はジョブで非同期に行う

- ステータス: Proposed
- 日付: 2026-10-23
- 関連 Issue / PR: E11（TASKS.md）、#107（ダミー規程の PDF）
- 関連ドキュメント: [ARCHITECTURE.md §2](../ARCHITECTURE.md)、[ROADMAP.md](../ROADMAP.md)（v0.2.0）、[ADR-0001](./0001-modular-monolith-spring-boot.md)、[ADR-0004](./0004-permission-prefilter.md)

## 背景（Context）

- v0.2.0 では、既存の規程の PDF をアップロードし、v0.1.0 の Markdown の規程と同じように**条単位・ページ番号付きで検索・引用**できるようにする。
- 既存のスキーマには、原本ファイル（`stored_files`）、版と原本の関連（`document_versions.source_file_id`）、条のページ範囲（`sections.page_from` / `page_to`）が用意されている。
- PDF の解析は、数ページで数百ミリ秒、大きなものでは数秒〜数十秒かかり、失敗もある（暗号化・画像だけのスキャン PDF・壊れたファイル）。アップロードのリクエストの中で同期的に行うと、タイムアウトや失敗時の扱いが難しい。
- ARCHITECTURE.md では、Phase4 以降に Python の ingest-worker（Embedding も担当）を置く構想がある。v0.2.0 の時点で別サービスを増やすと、運用・認可・CI の負担が大きい。
- 解析結果は誤ることがある（条の見出しの誤認、ヘッダー・フッターの混入）。公開前に人が確かめ、直せる必要がある。

## 決定（Decision）

1. **原本は S3 互換のオブジェクトストレージに置く。** ローカル・CI は compose の MinIO、本番は S3 などを想定する。backend は AWS SDK の S3 クライアントで扱い、接続先は設定で切り替える。DB には `stored_files`（保存キー・元のファイル名・MIME・サイズ・SHA-256）だけを持つ。
2. **アップロードは検証してから保存する。** PDF の先頭バイト（`%PDF-`）・サイズ上限（既定 20MB）・SHA-256 を確かめ、同じ内容の再アップロードは既存のファイルを使う。ファイル名は表示用にだけ使い、保存キーには使わない。
3. **解析は backend の中のジョブで非同期に行う。** `ingestion_jobs` テーブルをキューにし、backend のワーカーが `SELECT ... FOR UPDATE SKIP LOCKED` で1件ずつ取り出す。状態（待ち・実行中・成功・失敗）、試行回数、失敗理由を記録し、一時的な失敗は回数を限って再試行する。Kafka などのメッセージ基盤は使わない。
4. **テキストの抽出は Apache PDFBox で行う。** ページごとに抽出し、各ページのヘッダー・フッター（複数ページで同じ位置に繰り返し出る行）を除いてから、行頭の「第N条（見出し）」で条に分ける。本文中の参照が折り返しで行頭に来たもの（「第42条）。」など）は見出しとみなさない。条ごとにページ範囲を記録する。
5. **解析結果は下書きの版にする。** 取り込みの結果は `source_file_id` 付きの下書きの版（`body_markdown` も持つ）になり、既存の版の画面で内容・条の分け方を確かめ、直してから公開する。検索・権限は既存の版・セクションと同じ仕組み（ADR-0004 のプレフィルタ）をそのまま使う。
6. **扱えないものは、理由を付けて失敗にする。** 暗号化された PDF、文字を含まない（画像だけの）PDF は失敗にし、理由を画面に出す。OCR は v0.2.0 では扱わない。

## 検討した選択肢（Options）

### 原本の置き場所

| 選択肢 | 長所 | 短所 |
|---|---|---|
| S3 互換ストレージ（MinIO / S3）（採用） | 本番のクラウドと同じ API。DB が大きくならない。署名付き URL で直接配信もできる | compose のサービスが1つ増える |
| PostgreSQL の bytea | 追加のサービスが要らない。トランザクションでまとめて扱える | バックアップ・レプリケーションが重くなる。大きなファイルの配信に向かない |
| ローカルディスク | 最も簡単 | コンテナの作り直しで消える。複数台にできない |

### 解析の実行方法

| 選択肢 | 長所 | 短所 |
|---|---|---|
| backend の中のジョブ（PG のキュー）（採用） | 追加のサービスが要らない。DB のトランザクションと一緒に状態を管理できる | 重い解析が backend の CPU を使う（同時実行数で制限する） |
| アップロードのリクエストの中で同期的に | 実装が最も簡単 | 大きな PDF でタイムアウトする。失敗・再試行を扱いにくい |
| Python の ingest-worker（別サービス） | Phase4 の Embedding と同じ場所で動く。Python の PDF ライブラリが使える | v0.2.0 には過剰。認可・CI・運用の対象が増える |

### テキストの抽出

| 選択肢 | 長所 | 短所 |
|---|---|---|
| Apache PDFBox（採用） | Java で backend に組み込める。ページ・座標の情報が取れる。Apache License 2.0 | 複雑なレイアウト（段組み・表）の再現は限定的 |
| pdftotext（Poppler）を呼び出す | 抽出の精度が高い | 外部コマンドへの依存。イメージに入れる必要がある |
| 外部の文書解析サービス | 表・OCR まで扱える | 社内文書を外部に送ることになる。費用 |

## 結果（Consequences）

### 良い影響

- 取り込んだ PDF の条は、既存の Markdown の規程と同じ検索・権限・引用の仕組みにそのまま乗る。検索結果から「何ページ目か」まで案内できる。
- 原本と抽出結果を両方残すので、抽出を改善したら再解析できる。
- 解析の失敗が利用者の操作（アップロード）を止めない。失敗理由を見て対処できる。

### 悪い影響・受け入れるリスク

- compose に MinIO が増え、`make up` の起動が少し重くなる。
- 段組み・複雑な表・画像だけの PDF はうまく抽出できない。v0.2.0 では「人が確かめて直す」画面で補う。
- 解析が backend の CPU を使う。ワーカーの同時実行数を 1 にし、必要になったら Phase4 の ingest-worker に移す。

## 検証方法（Compliance）

- `data/pdf` のダミー規程10本を取り込み、条の数・条番号・ページ範囲が元の Markdown と一致することをテストで確かめる（ヘッダー・フッターの除外、参照の折り返しの誤認防止を含む）。
- アップロードの検証（PDF でないもの・サイズ超過・重複）と、ジョブの状態遷移（成功・失敗・再試行・同時に取り出さない）をテストする。
- 取り込んだ版も、権限マトリクステスト（#71）と同じ経路で絞り込まれることを確かめる。

## 見直す条件（Revisit when）

- OCR（スキャン PDF）や段組みの文書に対応する必要が出たとき。
- Phase4 で Python の ingest-worker を置くとき（解析をそちらへ移すかを判断する）。
- 解析の負荷が backend の応答時間に影響するようになったとき。
