# ADR-0013: 回答文の生成は既定でローカルの Ollama（qwen3.5:4b）を使い、引用を確かめてから画面に出す

- ステータス: Proposed
- 日付: 2026-10-28
- 関連 Issue / PR: #18（Epic E14）、E14-T1〜T4・T6（TASKS.md）
- 関連ドキュメント: [PRD §3 Phase5・§6 非機能](../PRD_KNOWLEDGE_NAVIGATOR.md)、[ARCHITECTURE.md §5.4〜§5.7](../ARCHITECTURE.md)、[ADR-0006](./0006-ai-service-stateless.md)、[ADR-0008](./0008-llm-provider-abstraction.md)、[ADR-0009](./0009-contacts-and-evidence-from-db.md)

## 背景（Context）

- ADR-0008 で、生成のプロバイダは ai-service の `ChatModel` で切り替え、既定は Ollama にすると決めた。**どのモデルを既定にするか**は v0.5.0 で決めることにしていた。
- 見る人が API キーなし・GPU なし（CPU）で `make up-ai` だけで試せることが大事（ADR-0008）。Codespaces は 4 コア・16GB を推奨している。
- 回答は日本語。条文の数値（金額・日数・期限）を正しく写せることが要る。ライセンスは、ポートフォリオで配布・紹介しやすいものがよい。
- ARCHITECTURE.md §5.5 は「引用を機械で確かめ、失敗したら回答文を捨てて通常の結果を出す」と決めている。一方で PRD の非機能要件は「RAG 初回トークン < 3 秒」で、回答文を1文字ずつ流す（ストリーミング）前提になっている。**流しながらでは、確かめる前の文章が画面に出てしまう**ので、この2つはそのままでは両立しない。
- CPU の小型モデルでは、回答文を最後まで作るのに数十秒かかることがある。

## 決定（Decision）

1. **既定の生成モデルは Ollama の `qwen3.5:4b` にする。**
   - Apache 2.0、2026-03 公開（2週間以上たっている）。日本語の評価が高く、4B なので CPU・16GB でも動く。
   - 考える過程を出す機能（thinking）は切る（Ollama の `think: false`）。速くするためと、回答に考える過程が混ざらないようにするため。温度（ばらつき）は 0 にする。
   - 環境変数は ADR-0008 のとおり `CHAT_PROVIDER`・`CHAT_MODEL`。`openai`・`azure_openai` のときは `CHAT_MODEL`（Azure はデプロイ名）を必須にし、既定のモデル名は持たない（クラウドのモデル名は入れ替わりが速いため）。CI とテストは `fake`（文脈の `[1]` を引用した決まった文を返す）を使う。
   - compose の `ollama-pull` で、Embedding のモデルと一緒に取り寄せる。
2. **回答文は、ai-service が最後まで作って確かめてから返す。** ai-service の `POST /v1/rag/answer` は1回の JSON の応答にする（ストリーミングしない）。応答は「回答文・使った引用の番号・回答できたか（できないときは理由）」。
3. **backend から画面へは SSE で、段階ごとに送る。** 1文字ずつではなく、次の順に送る。
   1. `results`: ナビゲーション検索の結果（制度・文書・窓口・FAQ の4ブロック。DB の値。ADR-0009）。検索が終わればすぐ送る
   2. `answer`（確かめた回答文と根拠）または `unanswerable`（理由。窓口は 1 で送ったもの）
   3. `done`
   - 生成の途中は、画面に「回答を作っています」と出す。生成に失敗・時間切れ（設定。既定 120 秒）のときも `unanswerable` にし、4ブロックの結果は残る。
4. **PRD の「RAG 初回トークン < 3 秒」を「最初の表示（4ブロックの結果）< 3 秒」に読み替える。** 回答文の速さは目標にせず、評価のレポートに時間を記録する。PRD をこの PR で直す。
5. **確かめる内容は機械的な照合にする**（ai-service。中身は E14-T3 で作る）。1つでも不合格なら回答文を捨て、`unanswerable`（理由: 確かめられなかった）にする。
   - 回答文の `[n]` が、文脈の番号の中にある。引用のない文がない（短い前置きは除く）
   - 金額・日数・割合・日付などの数値が、引用した条の本文にある（全角・半角、漢数字はそろえて比べる）
   - メールアドレス・電話番号の形の文字列がない（ADR-0009）
   - そもそも、検索の上位の点数が基準に届かないとき（根拠が無いとき）は、LLM を呼ばずに `unanswerable`（理由: 根拠が見つからない）にする。LLM が決まった言い方で「記載がない」と答えたときも同じ

## 検討した選択肢（Options）

### 既定の生成モデル（Ollama・CPU で動く大きさ）

| 選択肢 | 長所 | 短所 |
|---|---|---|
| qwen3.5:4b（採用） | Apache 2.0。日本語の評価が高い。CPU・16GB で動く | 4B なので、長い条文の要約や細かい言い回しは大きいモデルに劣る |
| gemma4:e4b | Apache 2.0（追加の利用規約あり）。軽い | 日本語の評価の情報が少ない |
| qwen3.5:9b | 品質が上がる | CPU では遅い。メモリを多く使い、Codespaces の推奨の大きさでは backend などと同時に動かしにくい |
| qwen3.5:2b | 速い | 数値の写し間違い・引用の付け忘れが増えやすい |
| 既定を OpenAI にする | 品質が高く速い | API キーと費用が要り、文章が外部に出る（ADR-0008 の方針に反する） |

### 回答文の届け方

| 選択肢 | 長所 | 短所 |
|---|---|---|
| 最後まで作って確かめてから、段階ごとに SSE で送る（採用） | 確かめる前の文章が画面に出ない。仕組みが簡単 | 回答文が出るまで待つ（CPU で数十秒）。4ブロックの結果を先に出して補う |
| 1文字ずつ流し、最後に不合格なら消す | 最初の文字が速く出る | 間違った文章を一度見せてしまう。消える画面は信頼を損なう |
| 1文ずつ確かめて流す | 速さと確かめるのを両立できる | 文の区切り・前の文との関係の扱いが難しく、作る量が大きい |

## 結果（Consequences）

### 良い影響

- API キーなし・外部送信なしで、根拠付きの回答を試せる。
- 画面に出る回答文は、必ず引用の照合を通ったものになる。
- ai-service の API が1回の JSON なので、テスト・評価のスクリプトから呼びやすい。

### 悪い影響・受け入れるリスク

- 回答文が出るまでの待ち時間が長い（CPU の 4B で数十秒の見込み。実測は E14-T6 の評価で記録する）。
- 取り寄せるモデルが増え、初回の `make up-ai` が遅くなり、ディスクも数 GB 増える。
- 機械的な照合は、言い換えた内容が根拠と合っているかまでは確かめられない。忠実さは RAG の評価（LLM による採点と人手の抜き取り）で測る。
- Ollama のモデル名（`qwen3.5:4b`）と大きさは、この環境から ollama.com に接続できず、直接は確かめていない。実装の PR で、オーナーの Codespaces で `ollama pull` できることを確かめる。

## 検証方法（Compliance）

- ai-service の pytest で、`fake` のモデルを使い、引用の照合（番号・数値・連絡先）の合格・不合格を確かめる。
- backend のテストで、SSE が `results` → `answer` / `unanswerable` → `done` の順に出ること、ai-service の失敗・時間切れでも `results` が出ることを確かめる。
- RAG の評価（E14-T6、`make eval-rag`）で、引用の正確さ（目標 95% 以上、ROADMAP M6）と、回答できない質問で `unanswerable` になる割合、回答までの時間を測る。

## 見直す条件（Revisit when）

- 評価で引用の正確さが 95% に届かないとき（大きいモデル、または1文ずつ確かめる方式を比べる）。
- 回答までの時間が、デモで使えないほど長いとき。
- Ollama で、日本語により強い同じくらいの大きさのモデルが使えるようになったとき。
