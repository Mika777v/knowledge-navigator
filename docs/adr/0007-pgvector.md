# ADR-0007: ベクトルは同じ PostgreSQL の pgvector に置き、権限で絞る SQL の中で検索して、キーワード検索と RRF で合わせる

- ステータス: Proposed
- 日付: 2026-10-26
- 関連 Issue / PR: E13-T3〜T7（TASKS.md）、#17（Epic E13）
- 関連ドキュメント: [ARCHITECTURE.md §4.5・§5.2・§5.3](../ARCHITECTURE.md)、[DOMAIN_MODEL.md §5.1](../DOMAIN_MODEL.md)、[TECH_STACK_DECISION.md D-05](../TECH_STACK_DECISION.md)、[ADR-0002](./0002-japanese-search-pg-bigm.md)、[ADR-0004](./0004-permission-prefilter.md)、[ADR-0006](./0006-ai-service-stateless.md)、[ADR-0008](./0008-llm-provider-abstraction.md)

## 背景（Context）

- 意味検索では、条・FAQ・制度の文章をベクトルにして保存し、質問のベクトルと近いものを探す。
- ADR-0004 で、権限は検索の**前に** SQL の WHERE で絞ると決めている。ベクトルを別のストアに置くと、権限の情報（公開範囲・所管部署・公開状態）を同期する必要があり、同期の遅れがそのまま情報漏えいになる。
- データの量は、ダミーデータで条が数百、将来も数万〜数十万の規模を想定している。
- DB のイメージ（`infra/docker/postgres`）は pgvector 公式イメージ（0.8 系）をもとにしており、`vector` 拡張はすでに有効になっている。
- ARCHITECTURE.md §5.3 で、ベクトル検索の「設定の名前・既定値・判定する場所・トグルを消す時期」は v0.4.0 の ADR で決めることにしていた。

## 決定（Decision）

1. **ベクトルは同じ PostgreSQL に pgvector で置く。** 別のベクトル DB は使わない。
2. **保存の形**: `embeddings` テーブルに、元の種類（`SECTION` / `FAQ` / `PROGRAM`）・元の ID・区切りの番号（`chunk_no`。長い条は区切るため）・モデル名・`content_hash`・ベクトルを持つ。一意の組は（元の種類, 元の ID, 区切りの番号, モデル名）。
   - **権限の情報（公開範囲など）はコピーしない。** 検索のときに、元の条・文書・制度・FAQ と結合し、キーワード検索と同じ `AccessPolicy` の条件で絞る。権限が変わっても、ベクトル側を直す必要がない。
   - ベクトルの次元は **1024** に固定する（`vector(1024)`）。次元の違うモデルに替えるときは、マイグレーションで列か表を足す。
3. **入れるもの**: 公開中の最新の版の条、公開中の FAQ・制度。**下書きと `CONFIDENTIAL` は入れない**（PRD の決まり）。ADR-0008 の「外部に送ってよい公開範囲」に入らないものも入れない。
4. **索引は HNSW（コサイン距離）**を、モデルごとの部分索引で作る。権限の WHERE で候補が減っても件数が足りなくならないよう、pgvector の反復スキャン（`hnsw.iterative_scan = relaxed_order`）を検索の SQL の中で有効にする。
5. **合わせ方**: キーワード検索の上位とベクトル検索の上位（それぞれ最大 50 件、どちらも同じ権限の条件で絞ったもの）を、**RRF（Reciprocal Rank Fusion。順位だけを使って合わせる方法。score = Σ 1 / (60 + 順位)）**で1つの順位にする。合わせるのは backend の navigation モジュールの `HybridSearchAdapter`（`SearchPort` の実装）。窓口の導出・制度経由の文書など、その後の組み立ては今のまま。
6. **検索に使うのは、今の Embedding のモデルで作ったベクトルだけ**（`WHERE model = 今のモデル`）。モデルを替えるときは、新しいモデルのベクトルを並べて作り、評価してから切り替える。
7. **オン・オフの設定**:
   - 名前は `knavi.search.vector.enabled`、**既定は `false`**（`application.yaml`）。compose の `ai` プロファイルでは環境変数で `true` にする。
   - 判定は navigation モジュールが検索のたびに行う。`false`、または ai-service を呼べないときは、キーワード検索だけ（今と同じ結果）を返す。検索ログには、ベクトル検索を使ったかどうかを残す。
   - **この設定は消さない。** AI を使わない構成（プロファイルなし）と、AI が止まったときの切り替えのために残す。v0.4.0 の評価で目標（言い換えの質問で +10 ポイント）に届いたら、`ai` プロファイルの既定をオンのままにし、届かなければオフに戻してリリースする。
8. 類似の条を出す API（E13-T6）も、同じ表と同じ権限の条件を使う。

## 検討した選択肢（Options）

### ベクトルを置く場所

| 選択肢 | 長所 | 短所 |
|---|---|---|
| PostgreSQL + pgvector（採用） | 権限の条件をキーワード検索と同じ SQL で書ける。同期が要らない。DB のイメージに入っている | 専用のベクトル DB より、大規模・高速な検索の機能は少ない |
| 専用のベクトル DB（Qdrant・Weaviate など） | ベクトル検索の機能・速度が高い | 権限の情報の同期が必要で、遅れが漏えいになる。運用するサービスが増える |
| OpenSearch の k-NN | キーワード検索とまとめて1つの製品で扱える | 今のキーワード検索（pg_bigm・Sudachi）を作り直すことになる。同期の問題は同じ |
| ChromaDB | 試すのが簡単 | 本番のストアに向かない。権限の二重管理（TECH_STACK_DECISION で本番には使わないと決めている） |

### 索引

| 選択肢 | 長所 | 短所 |
|---|---|---|
| HNSW（採用） | 速く、データを足しても作り直しが要らない。反復スキャンで絞り込みと両立する | 作るのに時間とメモリがかかる（今の規模では問題にならない） |
| IVFFlat | 作るのが速い | データが増えたら作り直しが要る。絞り込みと組み合わせると取りこぼしやすい |
| 索引なし（全件と比べる） | 結果が正確 | データが増えると遅くなる |

### 合わせ方

| 選択肢 | 長所 | 短所 |
|---|---|---|
| RRF（採用） | 点数の尺度が違うもの（pg_bigm の一致度とコサイン距離）を、順位だけで合わせられる。調整する値が少ない | 点数の差（大差か僅差か）は使わない |
| 点数の重み付きの和 | 点数の差を使える | 尺度をそろえる正規化と、重みの調整が必要 |

## 結果（Consequences）

### 良い影響

- 権限の判定は、キーワード検索・ベクトル検索・類似の条で同じ条件を使う。ベクトルの表には権限の情報がないので、古い権限が残ることがない。
- 追加のサービスが要らない（ベクトルの保存・検索は今の DB のまま）。
- 設定1つで、今のキーワード検索だけの動きにいつでも戻せる。

### 悪い影響・受け入れるリスク

- 次元を 1024 に固定するため、次元の違うモデルに替えるにはマイグレーションが要る。
- ベクトルの表のぶん、DB とバックアップが大きくなる（今の規模では数 MB 程度）。
- RRF の結果は、今の重み付きのスコア（ARCHITECTURE.md §4.3）と性質が違う。評価用の質問（100問）が下がらないことを確かめてからオンにする。

## 検証方法（Compliance）

- 権限マトリクステスト（#71）と同じ利用者・文書の組で、ベクトル検索・類似の条が、見えない条を返さない・件数に含めないことを確かめる。
- `CONFIDENTIAL` と下書きの条が `embeddings` に入らないことをテストで確かめる。
- `make eval` で、オン・オフそれぞれの成績を出し、言い換えの質問セット（E13-T7）で比べる。オフのときの成績が `data/eval/baseline.json` と変わらないことも確かめる。

## 見直す条件（Revisit when）

- 条の数が 100 万を超える、またはベクトル検索が応答時間の目標を超えるようになったとき（専用のベクトル DB や OpenSearch を比べる）。
- 次元の違うモデルに替えるとき。
- RRF では評価の目標に届かず、点数を使った合わせ方や並べ替え（rerank）が必要になったとき。
